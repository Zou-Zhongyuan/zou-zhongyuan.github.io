支付成功之后，订单为什么还要等商家接单？

顾客付款后，商家仍可能因为缺货拒单。要让系统知道该继续备餐还是等待退款，可以把订单状态和付款状态分开记录。

把职责放到对应的对象里

在 BCE（Boundary、Control、Entity）模型里，结账界面、支付网关接口和商家界面把外部事件交给控制器。控制器判断当前状态是否允许相应操作，再更新订单和付款记录。商家点击接单时，控制器检查订单仍在待接单状态，付款也已经成功。

一个订单的结账与退款路径
事件订单状态付款状态
提交订单待付款未付款
付款前取消已取消已关闭
确认付款待商家接单已付款
商家接单已接单已付款
商家拒单已拒单待退款
收到退款确认已拒单已退款

用失败路径检验设计

商家提醒发送失败时，订单仍然待接单，付款记录仍然有效。后续可以把通知写入独立的待投递记录，让推送重试与订单状态更新分开，商家也能从待接单列表查单。

模拟器覆盖同一事件重放、同 ID 异内容冲突，以及先收到拒单、补齐付款后再处理拒单。接入真实网关时，还需要定义超时与迟到的付款回调如何对账，以及接单和取消并发到达时哪次状态变化先提交。这些场景需要持久化和集成测试。

用 49、50、51 检查边界条件

假设批量导出每次允许 1 到 50 条记录。上界附近取 49、50、51，可以同时验证正常余量、恰好满额、超限三种结果。

如果把条件写成 count < 50，50 会被提前拒绝。如果把上限错写成 51，51 会被放行。49 则用来检查计数仍有余量时是否被提前标成满额。完整测试还应覆盖 0、1、2 和非整数输入。

def export_status(count: int) -> tuple[bool, int, bool]:
    if type(count) is not int or count < 0:
        raise ValueError("count must be a non-negative integer")
    return 1 <= count <= 50, max(0, 50 - count), count == 50


assert export_status(49) == (True, 1, False)
assert export_status(50) == (True, 0, True)
assert export_status(51) == (False, 0, False)
