Case Study 01 · RankLab Offline Evaluation

RankLab 案例研究：全候选与抽样候选为什么会让推荐模型排名反转？

在推荐系统离线评测中，抽样候选协议常被用来降低全库打分开销。RankLab 在 GroupLens 官方 MovieLens Latest Small 与 MovieLens 1M 上，用同一套嵌套全局时间切分与 3 个随机种子对比了 Full-Corpus（全量可用候选池）与 Sampled-100（真实协议：evaluation.py 取每名用户在测试窗口内的全部可用未见正例 + 至多 99 个均匀抽取的未看负例，打分后按候选预算 M = 100 截取，并非固定 1+99）：全候选下显著胜出的两阶段重排模型，切换到抽样候选后名次骤降 4 位发生显著反转。

一、反转机理：抽样协议把「头部精排」扭曲成了「粗粒度召回」

为直观展示均匀负采样如何压缩全库排位，先看一个简化的单正例教学示例：设可用候选池总数为 N（剔除用户截至 T_dev 已评分影片），若仅对 1 个正例均匀无放回抽取 99 个负例，全库真实排位 r（1 ≤ r ≤ N）对应的期望抽样排位为：

E[r_sampled] = 1 + 99 × (r - 1) / (N - 1) （单正例 1+99 教学示例）

在 RankLab 真实实现的 sampled_100 协议（全部可用未见正例 + 至多 99 个负例，之后按 M = 100 截取）中，多正例用户的候选池同样把大规模未看负例压缩至至多 99 个，因此也可能出现排位压缩（Krichene & Rendle, KDD 2020）。代入 MovieLens 1M 的可用目录规模 N = 3,669（ml-latest-small 为 N = 8,187）即可看出扭曲根源：

  • 头部压缩失真（教学示例直觉）：在 N = 3,669 的单正例示例下，全库仅排在第 r = 38 名的物品，进入抽样池后的期望排位约为 r_samp ≈ 2.0；即便全库跌至 r = 335 名，期望排位仍在第 10 名附近。真实 sampled_100 协议同样大幅削弱了负例竞争密度。
  • 两阶段重排反转（BPR-MF + HistGBDTRerank vs BPR-MF）：全候选 NDCG@10 奖励将正例从第 20–100 名精准推入前 10 名的头部排序分辨力，因此 HistGBDTRerank 在 ml-1m 全候选下将 BPR-MF 从 0.26695（#5）显著提升至 0.28819（#2，+7.96%，p < 0.001）。但抽样 NDCG@10 实质退化为衡量全库约 Top-370 的粗排覆盖；仅对 Top-100 候选做非线性分裂重排的树模型引入了局部打分方差，在 Sampled-100 中反而跌至 0.72407（#6），显著落后于未重排的 BPR-MF（0.76598，#2，-5.47%，p < 0.001）。
  • 协同过滤与矩阵分解倒置（ItemCF vs BPR-MF）：在 ml-1m 全候选下，ItemCF（0.28004，#3）显著优于 BPR-MF（0.26695，#5，差值 -4.68%，p < 0.001）；但因 BPR-MF 拥有更高的 Recall@100 上限（0.32964 vs 0.30467）与目录覆盖率（Coverage@10 = 32.68% vs 5.21%），在 Sampled-100 下反超为 0.76598 vs 0.74464（+2.87%，p < 0.001）。
  • 小数据流行度 3.25× 虚高：在目录更稀疏的 ml-latest-small（N = 8,187）上，Sampled-100 将纯 Popularity 的 NDCG@10 从 0.24104 虚高 3.25× 至 0.78399，把全候选优于流行度的 BPR-MF + LogisticRerank（0.27537 > 0.24104）扭曲成落后流行度 -28.1%（0.56387 < 0.78399）。

四、实验局限与诚实未执行边界（Limitations & NOT_EXECUTED）

1. 显式评分 MNAR 与曝光偏差

使用 rating >= 4.0 构造隐式正例仅衡量“已观测评分条件下的偏好排序”，存在显著非随机缺失（MNAR）与历史曝光偏差，离线增益不能直接外推为工业线上 CTR / CVR 收益。

2. 长跨度冷启动与新片未上市上限

ml-latest-small 横跨 22 年且 68.75%（66/96）测试用户为 cold_0 新用户，同时有 655 部未上市新片（占测试正例 15.04%）超出因果候选池；线性重排大盘均值受老片年龄负权重拖累（剔除 Pop & Recency 组后升至 0.30830），但在 Heavy 20+ 老用户上仍提升 +77.4%。

3. 生成式检索码本桶碰撞瓶颈

TIGER-Seq2Seq 在 ml-1m 解码 5,017,998 束实现 0 非法幻觉、Coverage@100 = 60.78% 全场第一，且 MPS→CPU 解码提速 575×；但轻量 3×16 残差 K-Means 码本在桶碰撞深度 98–345 时限制了头部 Top-10 细粒度分辨力（0.19894）。

4. 未执行扩展明确声明（NOT_EXECUTED）

LightGBMRerank 因宿主机缺 libomp.dylib 标记 NOT_EXECUTED（已由纯 NumPy HistGBDTRerank 同构替代）；依赖商业 API 的在线 RankGPT 列表重排与 7B TALLRec LoRA 微调按零付费与 16 GB 本机内存边界均如实标记 NOT_EXECUTED。

Note 02 · State Machine Design

支付成功之后，订单为什么还要等商家接单？

顾客付款后商家仍可能因缺货拒单。把订单履约状态（OrderStatus）与资金结算状态（PaymentStatus）正交拆开，系统才能在正常备餐、付款前取消与异步退款之间保持无歧义流转。

BCE 控制器下的双状态演进路径
外部事件订单状态付款状态
提交订单待付款未付款
付款前取消已取消已关闭
确认付款待商家接单已付款
商家接单已接单已付款
商家拒单已拒单待退款
退款完成已拒单已退款

配合按 event_id 校验载荷摘要的幂等守卫与事务外盒（Transactional Outbox），即使网关重复投递或先达拒单后到付款确认，状态机依然收敛至一致终态。完整可执行实现与 16 项自动化测试见公开仓库 Campus Checkout ↗。
